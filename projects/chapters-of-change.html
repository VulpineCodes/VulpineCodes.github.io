Chapters of Change

A donation platform that moves comics and manga from donors to the kids who'll love them.

Chapters of Change connects people with comics and manga to spare with schools and libraries that want them. Donors list collections, organizations request them, and a structured approval workflow — with idempotent submissions and strict authorization — carries each donation from offer to delivered.

Why it exists

I grew up in Lagos loving art, comics, and storytelling. Stories were how a lot of us first imagined lives bigger than the one in front of us — and access to them was never evenly distributed. The kid with a stack of manga passed hand-to-hand through a classroom got something real from it.

Chapters of Change is my attempt to build the logistics for that: a trustworthy pipeline between people who have stories to give and institutions that put them in front of kids.

My role: Solo designer and engineer — domain modeling, API, auth, frontend, and tests.

Architecture

Engineering decisions & trade-offs

Workflow as an explicit state machine

Donations move through named states (pending approval → in transit → delivered → completed) with guarded transitions. Illegal moves — like approving a rejected request — return 409 instead of corrupting state, and terminal states reject everything.

Idempotency at the API boundary

Donation submissions carry idempotency keys, so a retried or double-submitted request returns the original record flagged as deduplicated rather than creating a duplicate donation.

Hand-rolled JWT, on purpose

The HS256 signer/verifier is implemented directly on Node's crypto — algorithm pinned, timing-safe comparison, expiry enforced — because understanding the token format beats importing it. Passwords are bcrypt-hashed, and login failures return an identical generic 401 for unknown emails and wrong passwords alike.

Store behind an adapter

Persistence sits behind a store interface with in-memory and Prisma adapters, selectable by environment. The workflow logic is tested against the verified in-memory adapter; the Prisma adapter fails fast without a database URL rather than pretending to work.

Testing & evidence

  • 56 automated tests across the domain state machine and application services — all passing.
  • A real-HTTP smoke test exercises the full path: register, log in, list, donate, approve, deliver, complete — plus idempotent replay, cross-organization 403s, and approve-after-reject 409.
  • TypeScript typechecks clean; the Next.js production build succeeds.

Results

  • End-to-end donor → recipient flow verified over real HTTP against the booted API.
  • 56 / 56 tests passing; investigation of every authorization branch covered (owner, cross-org, anonymous).

Honest limitations

  • The Prisma adapter has not yet been run against a live PostgreSQL instance; the verified path is the in-memory store.
  • The BullMQ notification worker core is tested, but a live Redis run is still pending.
  • Not yet deployed — no public demo URL.
