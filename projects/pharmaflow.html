PharmaFlow

Serious data infrastructure for small pharmacies.

PharmaFlow is the operations platform small pharmacies never get: idempotent ingestion of inventory and sales, data-quality quarantine, analytics in under a second, streaming that survives crashes, and an API serving it all. Sized for a family pharmacy. Engineered like it matters, because it does.

Why it exists

My father ran a small pharmacy in Lagos. When COVID hit, foot traffic vanished and customers stopped coming in, but the business still ran on paper ledgers and phone calls to coordinate deliveries. Nothing stopped exactly. It just ran blind.

PharmaFlow is the platform I wish had existed for him. It handles the unglamorous core: what is on the shelves, what is expiring, what sold, what is missing. No patient data, no prescriptions. Just operations, done properly.

My role: Solo project. Ingestion, storage, analytics, streaming, API, benchmarks: all mine.

Engineering decisions and trade-offs

Idempotency as a foundation, not a feature

File hashes and row hashes make every import safely replayable, verified across separate processes against the same database file. Re-running yesterday's import is a no-op, not an incident.

A bottleneck, measured then fixed

At 50,000 rows the DuckDB analytics took 61.6 seconds. Profiling showed the SQL took 0.07 seconds; the other 59 were row-by-row Python inserts. A bulk appender load brought it to 0.49 seconds, and a correctness gate asserts the new loader returns results identical to the old one.

Exactly-once effect from at-least-once delivery

The streaming layer commits offsets only after processing and dedupes by event ID. In the crash test the consumer dies after applying 2 of 4 events, before committing. On restart it replays all four and the final stock is exactly right. Poison events go to a dead-letter queue instead of wedging the consumer.

Honest benchmarks or none

Every performance number ships with its conditions: machine, versions, dataset seed, single-run caveats. Numbers measured on a laptop are labeled as such. They are evidence about the code, not marketing about production scale.

Testing and evidence

  • 60 pytest tests passing, covering cross-process idempotency, crash recovery, streaming crash tests, and the analytics correctness gate.
  • dbt executed for real against DuckDB: seeds, models, and all 8 data tests green.
  • Benchmarks at 1k, 10k, and 50k rows, committed with full conditions in benchmarks/RESULTS.md.

Results

  • Ingestion near 7,000 rows per second at 50k rows. Re-importing the same 50k rows takes 0.145 seconds, because the file hash says nothing changed.
  • Analytics at 50k rows: 61.6 seconds down to 0.49 after the bulk-load fix, with identical results.
  • Streaming crash test: kill the consumer mid-batch, restart, and the final stock is exactly right. 90 units, not 80.

Honest limitations

  • The Kafka/Redpanda and PostgreSQL adapters are written and reviewed but unverified. No broker or database server exists in the local environment; the tested paths are the file-log broker and the SQLite store.
  • Terraform is reviewed for consistency but unapplied. Grafana and Prometheus remain Compose declarations.
  • Benchmarks are local single-machine figures, explicitly not production scale. Not deployed.

Status: Active development, milestone 7. The repository’s STATUS file tracks what is verified versus pending, in the open.
